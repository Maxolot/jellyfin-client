# Install, configure and operate

The server must be Jellyfin12 on .NET10, with a working configured Jellyfin FFmpeg
and FFprobe. The plugin uses those paths at execution time, after initialization.
No separate daemon, queue server, database, subscription or media library write
access is required. Use a read-only media mount wherever possible.

## Install

1. Build or obtain the versioned plugin ZIP and matching source archive/checksums.
2. During an idle maintenance window, place Jellyfin.Plugin.NativePreviews.dll in
   a dedicated subdirectory of the server's plugins folder. Keep the previous
   plugin version and configuration for rollback.
3. Restart Jellyfin. Confirm Native Previews appears as Active and authenticated
   GET NativePreviews/Capabilities reports Version1.
4. Open Dashboard → Plugins → Native Previews. The default budget is2GiB including
   imports/work and the free-space reserve is2GiB. Choose limits appropriate to the
   actual filesystem. Prefer a fast server-owned data directory, separate from media.
5. Approve a short scene in the administrator page or import an existing approved
   clip through the API. Verify the resulting scene, audio and colour once before
   expanding coverage. The client resolves available scenes automatically.

A release manifest generated by scripts/package.py can be hosted at the operator's
chosen HTTP(S) URL and added to Jellyfin's plugin repositories. Its download URL
is deployment data, not a personal endpoint compiled into the plugin. Archive,
source and checksums should remain accessible together. Do not publish imported
media or the plugin's data directory as an installation package.

## Prepare and migrate

The administrator page searches the current library instead of requiring an ID
list in source code. A movie uses its local media; a series defaults to S1E1. An
explicit source episode can be supplied by API. Set start/duration and approve the
scene. The original file remains intact. Ordinary users can request prepared clips
but cannot approve, upload or select arbitrary source paths.

Existing approved MP4 clips can be uploaded as multipart field file, one per logical
item. The plugin probes the file and prepares both supported variants. This keeps
an older deployment's selection while moving ownership to the plugin catalogue.
Keep the original clip folder/configuration until migration is verified, then
remove the old static registry/mount from the client deployment. Do not commit
that private migration map or footage.

## Optional automatic coverage

Automatic selection is off by default. If an administrator explicitly enables it,
the first authorized manifest request for a movie, series or episode creates one
bounded scene near 8% of its duration; series use S1E1. This percentage does not
identify spoilers. Clips are generated lazily, one job at a time, and an image is
shown until ready. Previously approved scenes take precedence. Automatic scenes
are marked separately, and disabling the option prevents them from being served
or newly queued. The bounded cache can evict clips, which are regenerated later;
coverage does not mean every clip is simultaneously stored on disk.

## Resource policy and failures

One bounded64-job queue and one encoder. Paused playback does not block generation;
active playback prevents a job from starting and interrupts/requeues a running job.
CPU threads(default2) and job/probe deadlines are bounded. Auto uses configured
NVENC or Linux Intel QSV when supported, otherwise CPU; encoder failure can retry CPU. Other hardware
pipelines remain a future adapter, not an implicit promise of acceleration.

The cache evicts least recently used and idle generated files while retaining scene
choices. Approved uploads are retained input within the same budget; if they alone
fill it, new work is refused rather than deleting sources. Clips missed after
LRU eviction can regenerate in the background when requested. A library source
change invalidates the old scene output; recheck the scene before preparing again.

Missing plugin/clip, unsupported formats, lack of space, failed probing or encoding
leave artwork in the client. Detailed failures stay in server logs; client responses
contain bounded status categories. A running response holds an open stream so LRU
removal does not cut off a range already being served. Native/ASS/bitmap subtitles
are not burned into previews; audio uses the first available source audio track.

Inspect codec and HDR colour on the actual server build. HDR10/HLG use software
SDR tone mapping; do not assume every Dolby Vision profile is supported by that
pipeline. Existing approved SDR imports remain an alternative. There is no claim
of physically tested Safari/iOS/TV compatibility in the initial release.

## Backups and rollback

Back up scene metadata, approved imports and plugin configuration. Generated cache
files can be omitted; they regenerate. The ticket key is private and must not be
published. Losing it invalidates old preview URLs without exposing account tokens.

To roll back, restore the prior plugin DLL/configuration during an idle restart
window. Missing provider support safely returns the client to posters or its
optional static compatibility configuration. Never use item deletion APIs to remove
preview cache: Jellyfin item deletion can remove original media. Cache cleanup must
remain inside the plugin-owned cache directory.
